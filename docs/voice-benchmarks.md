# 语音管线性能基线

**测量时间:** 2026-05-01(实施验收 v1)
**环境:** 本地 macOS,Wi-Fi,Chrome 最新版,默认 Mac 麦克风。
**测量方法:** 跑了 18 轮真实 push-to-talk(用户人工按住空格说话),`LessonController` 内插 `[bench]` 打点输出到浏览器 Console。其中 4 轮(r7/r10/r11/r18)因按住时间过短(< 1.2 秒)豆包没识别出 utterance、final 帧没回来,被 9 秒 timeout 兜底救回 — 这 4 轮不计入延迟统计,实际有效轮 14 个。

## 实测(14 轮成功,本批数据采集时尚未开 mic 预热)

| 指标 | 目标 | 实测中位 | 实测 90 分位 | 备注 |
|------|------|---------|--------------|------|
| 用户松手 → ASR final | < 500ms | 594ms | 650ms | 接近目标,后续 mic 预热应进一步降 |
| ASR final → LLM 第一句 token | < 1s | 3976ms | 4520ms | **严重超目标**,MiMo 上游 first-token 慢 |
| LLM 第一句 token → TTS 首 PCM 包 | < 500ms | ~2200ms | ~2700ms | 流式 JSON 解析到 speech 字段后才能 push TTS |
| **首音频总延迟** | **< 2s** | **6212ms** | **7220ms** | **严重超目标**,LLM 是瓶颈 |
| 5 轮平均 round-trip | < 3s | 8860ms | 9742ms | round-trip 含 AI 说话整段时长,不是单纯首响指标 |

> **结论:** 用户提出的 P0 问题"按住空格说话头几个字录不上"已经定位为 mic 启动延迟(getUserMedia + worklet + WS 串行 ≈ 200-500ms),已加 prewarm 修复;录音过短(< 1s)被豆包丢弃的情况靠客户端 9 秒 timeout 兜底自动恢复。

> **下一步:** 首音频 6 秒主要被 MiMo first-token(4 秒)拖累,前端再优化也只能省几百 ms。要么:① 换更快的 LLM 模型;② prompt 改造让 LLM 强制最先吐 speech 字段(目前依赖状态机解析 — 如果 LLM 先吐 actions/state_update,SpeechExtractor 要等到 speech 字段才 emit,首字延迟更大);③ 客户端在 thinking 状态播一句"嗯..."占位音遮蔽延迟。
>
> **2026-06-21 更新:③ 占位音已停用。** 实测发现本地预渲染「嗯,让老师看看哦~」会在 ASR/LLM/TTS 正常运行时插入,听感像系统没检测到孩子发音,因此 `LessonController` 不再 fetch 或 enqueue `public/audio/thinking-filler.pcm`。真正减延迟仍需 ① 换更快模型或重构。
> **ASR `end_window_size`(800ms)未改:** 本项目 push-to-talk 在松手时发 `finish` 负序号控制帧强制终结,不依赖豆包静音窗口自动终结,故 `end_window_size` 不 gate 我们的延迟,降它是 no-op(还会影响潜在的自动终结路径),因此保持不动。

## 备注

- 跑测时关闭其他大流量应用(避免网络抖动)。
- 第一次 round-trip 因为 TTS WS 还没有 cache,可能比第 2 轮起慢 ~200ms。本批 r1 已包含 TTS 长连握手(~3.7s 的 ConnectionStarted),开场白阶段已经握手完,r1 之后没再 ConnectionStarted。
- 失败原因(timeout 4 次)分析:豆包 ASR 在收到 PCM < ~10 个包(< 2 秒)时,识别置信度不够,utterance 全部 `definite=false`,即使我们发了负序号终止包,豆包仍不返回 isFinal=true 的帧 → 客户端 9 秒 timeout 兜底。**用户体感:这种情况下小朋友按下立即松开 / 按下还没说话就松开,系统会"卡 9 秒后让你再说一次"**。本身不是 bug,是产品体验,后续可考虑 stopListening 时检测录音时长 < 500ms 直接 fallback、不进 thinking。

## 真实课堂 smoke(`SMOKE_BASE=:3001 pnpm smoke:lesson`,真实 system prompt,11 步)

- 每步总耗时(含路由 + guard + SSE 消费):4.5s ~ 14.2s,中位 ~7.3s
- 对比 MiMo 时代整轮 ~6s:**DeepSeek-V4-Pro 生成段更慢、输出更长,尾部(~1/10 轮)可超 15s**
- 因此 LLM 服务端总超时 15s → **20s**,client chatWatchdog 20s → **25s**(超时误杀正常轮变成 SSE error,孩子白等一轮)
- 三次 smoke:修复 sentence 卡劫持 bug 前 2/11;修复后 10/11(1 轮 15s 超时误杀);上调超时后 **11/11 + UI 2/2**

**体感注意:** 孩子等待老师响应的时间比 MiMo 时代更长(中位 ~7s vs ~6s,尾部可到 14s+)。如实际课堂体感不可接受,候选动作:换更快的模型(改 `.env.local` 的 `LLM_MODEL` 即可)/ prompt 约束 speech 更短 / 恢复 thinking 占位音。

## DeepSeek-V3.2 延迟与超时处理(2026-10-25)

背景:2026-10-24 默认模型改为 `deepseek-ai/DeepSeek-V3.2`(SiliconFlow)后,UI 重构期间多次 `smoke:lesson` 文本段出现「模型服务响应超时」(旧的单一 20s 总超时)。服务端要等整轮回答出完才让老师开口,所以孩子等待时间 = 整轮 LLM 总耗时。

**直连探针**(lesson 形状 prompt ~2.3k 输入 token,json_object + 流式,20 次):

| 指标 | 中位 | p90 | 最大 |
|---|---|---|---|
| 首 token | 0.83s | 2.3s | 3.4s |
| 生成段 | 5.6s | 8.1s | 8.5s |
| 整轮 | 6.3s | 9.4s | 10.0s |

- 生成速率 16~24 tok/s,最慢一次 9.3 tok/s;输出约 90~135 token/轮。
- 未开推理:`reasoning_tokens=0`,传不传 `enable_thinking:false` 结果一样,首 token 慢不是「思考」造成的。
- 另外几批共 ~56 次中有 4 次首 token 7~9s(约 7%),属于服务商排队。

**真实课堂 smoke 前后对比**(各 3 遍 × 11 步,`VOICE_MOCK=false PORT=3001`,animals 课):

| 方案 | 结果 | 整轮中位 | 最长 | 超时作废 |
|---|---|---|---|---|
| 旧:20s 总超时 / client 25s | 2 遍 11/11,1 遍 10/11 | 6.4s(LLM 段) | 20.0s(超时) | 1 / 36 轮 |
| 新:4s 首 token 对冲 / 10s 卡住 / 30s 总上限 / client 35s | 3 遍 11/11 | 6.5s(含路由) | 18.7s | 0 / 36 轮 |

- 新方案下 36 轮里对冲触发 4 次(约 11%),2 次对冲请求先出字;失败那类「首 token 8.9s + 慢生成」的轮次不再整轮作废。
- 样本小(各 36 轮),结论是「明显减少超时作废」,不是「消除」;慢生成轮仍可能接近 19s,孩子会等得久。进一步缩短需要减少输出 token(prompt 约束 speech 更短)或让老师在守卫跑完前先开口,属于另外的改动。

## Realtime 评估顺序对比(2026-11-11,真实模型 + 合成语音)

目的:去掉老师在调 `record_assessment` 前说的铺垫("let me check"一类),并缩短孩子说完到老师出声的等待。工作负载相同:`realtime-browser-smoke.ts --live --attempt-loop 12`(标准场景 + 连续 12 次作答,animals,合成成人语音,自动划轮)。每个方案只跑了 1 次;数据来自 `realtime_responses` 表和 `server.log`。等待时间是估算(以提供方报告的语音时长推算孩子停止说话的时刻,早于 0 的记 0)。

| 方案 | 评估次数 | 调工具前说了什么 | 等待中位数 | 回应数 | 老师语音 | 估价 |
|---|---|---|---|---|---|---|
| 改之前:工具先行,不许先说话 | 13 | 10 次不说话;3 次英文铺垫("Nice try—I'll note what you said…") | 约 1.6 s(工具先行的轮次约 2.1 s,不调工具的轮次约 0.8 s) | 41 | 165 s | $0.52 |
| 方案一:先说完整反馈和下一步,再调工具,模型标 `turn_complete` 后不追加回应 | 10 | 10 次都先说;其中 7 次只说了"我们换个场景再试试"就停,之后没有人再开口 | 约 0.2 s | 21 | 136 s | $0.41 |
| 方案二:先说一句短反应,调工具,照常追加回应给下一步 | 13 | 13 次都先说;11 次带"我先把这次练习记下来,然后继续"的尾巴 | 接近 0 | 33 | 216 s | $0.56 |

- 回忆提问不带答案的规则在三次方案二运行里都生效("公园里跑来一只小狗,它是?")。
- 五次运行合计约 $2.38。
- 结论:要稳定去掉铺垫,需要让说话的回应里根本没有评估工具,由应用另起一个不出声的回应做评估(提供方的 out-of-band response)。当天已实现,见下一节。

## Realtime 评估回应(out-of-band,2026-11-11)

做法:老师的回应里不再有评估工具;孩子每次输入提交后,应用另发一个不进入会话、只出文字、强制调 `record_assessment` 的回应做评估,和老师的回应并行。

### 接口行为小实验(WebSocket 直连,合成语音,6 轮,几美分)

脚本是一次性的,没有进仓库。会话用 `semantic_vad`(`create_response`、`interrupt_response` 均为 true),评估回应带 `conversation: "none"`、`output_modalities: ["text"]`、自己的 `instructions` 和 `tools`、`tool_choice: "required"`。

| 问题 | 结果 |
|---|---|
| 能否和 VAD 创建的回应同时进行 | 能。输入提交后立即发出,两个回应都正常完成,没有 `conversation_already_has_active_response` |
| 能否听到会话里孩子的音频 | 能。卡片是 dog、孩子说 cat,记 heard "cat"、wrong;孩子问"这是小狗吗",记 not_attempt 并写出原话 |
| 孩子再次开口(VAD 打断)时会不会被取消 | 不会。老师的回应以 `turn_detected` 被取消,评估回应照常完成 |
| 不带 id 的 `response.cancel` 会不会取消它 | 不会,只取消会话内的回应 |
| 会不会往会话里加 item | 不会(`conversation_id` 为 null,没有 `conversation.item.added`) |
| 从创建到完成 | 0.9 到 1.8 秒(短上下文) |
| 不换 instructions、不带工具 | 它会以老师的口吻回一段文字,没有用;必须带评估指令和强制工具 |

### 整课工作负载(与上一节同一负载,1 次运行)

`realtime-browser-smoke.ts --live --attempt-loop 12`,animals,合成成人语音,自动划轮。

| 指标 | 结果 |
|---|---|
| 老师说话的回应 | 21 个,没有一个带铺垫;作答后的回话形如"对,dog!现在想象院子里有一只狗,你看到它,它是?" |
| 评估回应 | 18 个,全部 completed,0 次失败,0 次重发 |
| 判定 | 13 次作答全部保存(跟读 `mastered=false`,换情境后自己说出 `mastered=true` 2 次);5 次请求("慢一点好吗""再讲一遍好吗"等)全部判 not_attempt,没有计入作答 |
| 评估耗时(创建到完成) | 1.4 到 3.6 秒,中位数约 2.3 秒;不在孩子等待的路径上 |
| 孩子说完到老师出声(估算) | 中位数约 0.9 秒(n=18,最大 4.0 秒);上一节的工具先行基线约 1.6 秒,短反应方案约 0.3 秒 |
| 回应数 / 老师语音 / 估价 | 39(老师 21 + 评估 18) / 129 s / $0.42 |

- 一次运行、合成语音。真人孩子的发音、外放环境和整节课长度下的表现要看下一节真人课:`assessment` 日志(结果、是否保存、耗时)、`assessment failed`、`realtime_responses` 里 `kind=assess` 的行。


## Realtime 划轮档位 low → medium(2026-11-14)

起因是 2026-11-14 两节真人课(instruments,桌面 App,外放模式开,`semantic_vad` eagerness `low`):孩子说完到老师开口的等待两极分化。

| 指标 | 第一节 | 第二节 |
|---|---|---|
| 有记录的回话等待 | 40 次 | 37 次 |
| 小于 1 秒 | 22 | 18 |
| 1 到 4 秒 | 10 | 9 |
| 不少于 4 秒 | 8(其中 6 次在 6.3 到 8.8 秒) | 10(其中 8 次在 6.4 到 8.3 秒) |
| 中位数 / p90 | 0.69s / 7.0s | 1.03s / 7.8s |

- 长等待发生在提供方判定「说完了」这一步:`child speech` 日志(收到 speech_stopped 时打印)比按音频时间戳算出的说话结束点晚 6 到 7 秒,之后约 1 秒老师出声。官方 API 参考写明 low / medium / high 的最大等待是 8 / 4 / 2 秒。
- 改为 `medium` 后的真实 API 验证(同日,合成成人语音,animals,能力场景 1 次,14 个回应,用量完整):6 段语音的回话等待 0.39 到 1.68 秒;6 段语音对应 6 次评估,没有一句被切成两段;评估耗时 1.2 到 1.7 秒。
- 新增的 `vadWaitMs` 在这 6 段里都是 0。合成语音句尾干净,提供方立刻判定说完,没有可测的等待;另外 speech_started 的到达本身比真实开口晚几百毫秒,所以这个字段会少报几百毫秒,只适合看秒级的等待。
- 同日两次真实短整课(合成语音逐词作答,animals)补到了上限的证据:52 段语音里 `vadWaitMs` 有 25 段不为 0,最大 3.3 秒,没有一段超过 4 秒;回话等待最大 5.4 秒(`low` 时真人课最大 8.8 秒)。也就是说 `medium` 下单个词的作答仍可能等 3 秒多,但不再有 6 到 8 秒的等待。
- 没有验证到的:真人孩子犹豫、拖音时 `medium` 会不会抢话或把一句话切成两段。合成语音复现不了,需下一节真人课看 `vadWaitMs` 和 `reply wait`。

## Realtime 短整课,老师提示词更新后(2026-11-14)

真实模型 + 合成语音,animals,断点剩 2 个词 + 2 道题,`--live --full --resume-short`。这是「评估结果写回老师」「先放卡再提问」「全部词过关就进入练习」三处提示词改动的验证。

| 运行 | 结果 | 回应数 | 时长 | 估价 |
|---|---|---|---|---|
| 只加「评估结果写回」和「整句先放句子卡」 | 没有结束,10 分钟后手动停止 | 92 | 617s | $1.22 |
| 再加「先放卡再提问」「全部词过关就进入练习」 | 完成(课程 done) | 31 | 158s | $0.33 |

- 第一次运行的问题:两个词约 1 分半都过关后,老师没有调用 `start_practice`,一直让孩子回忆屏幕外的词(猫、狗、鸭子),屏幕停在 frog 卡;合成的孩子只说屏幕上的词,应用按屏幕卡判对,老师的问题和判定对不上。根因是 2026-11-12 加的「收尾提示未到就用同一批词继续练」没有限定「还有词没过关」,那次改动之后没有重跑过真实短整课。
- 第二次运行:续课回忆的两个旧词都是先 `show_card` 再提问,作答被记录(其中一个判为过关);两个新词各「跟读一次、换情境再问一次」后过关;随后进入练习题并完成。8 条评估结果消息写入(7 条 correct、1 条 not_attempt),老师没有念出来,没有工具被拒,评估 0 失败。
- 第三次运行(再加「续课开场先放卡再提问」和跟读提醒,同一工作负载):完成,36 个回应。开场回应先 `show_card` 放出一张已过关的词卡,随后一句话里问候并提问(「你好，欢迎回来。草丛里跳出一只小猫，它是？」),没有触发沉默提醒;回忆的 3 个旧词都是先放卡再问。10 条评估结果消息写入。两个新词都是跟读一次后换情境就过关,所以「跟读对满 2 次的提醒」在这次运行里没有触发,它只有单测覆盖。
- 仍然存在的:换卡时老师会说一句流程话(「我们看看下一张卡片」);进入练习前老师先放了一张句子卡并邀请跟读,紧接着应用切到了练习题,这一句邀请落空。
